## Dependency notes

- 001, 002, 003, and 004 do not depend on each other. 001 and 002 make the slow customer reads cheaper. 003 stops the browser from waiting on them in series and from refetching them on every navigation. 004 removes the cold start, which is a different delay (first request after idle, often several seconds).
- Commit `1ad0606` (`Reduce round trips to pg`, on `main` before this index) already stopped row-level security from running `set_config` before and after every statement. Do not rework `api/remitx_api/db/rls.py`. If QA was built from a commit before `1ad0606`, ship that commit before judging these plans: it was the largest per-request tax.
- Local evidence that the API is fine when Postgres is local and the process has a CPU: `tools/loadtest/results/20260927-032245/summary.json`, compute tier `medium` (1 CPU), 10 users, HTTP median 55ms. Tier `small` (0.1 CPU) median 1100ms is CPU starvation in that harness, not the production shape (Cloud Run API is `1000m`).

## Why requests are over a second

The API is Cloud Run in `africa-south1`. Neon is created without a region (`infra/data/modules/neon/main.tf`), and Neon is not in Johannesburg, so every SQL statement is a cross-region round trip. A customer page's standing read issues about six statements and `GET /accounts` issues two more per account. The browser does not start those calls together, and it refetches them whenever a page mounts, because React Query's `staleTime` defaults to 0. Separately, the API service scales to zero, so the first request after idle is a cold start.
