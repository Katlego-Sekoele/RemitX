# End-to-end integration slice + Alembic migrations

**Date:** 2026-08-19
**Status:** Implemented
**Branch:** `feat/integration-slice`

## Purpose

Prove that every moving part of the RemitX stack talks to every other one,
before any domain logic depends on it. One message travels the full path:

```
browser → FastAPI → Postgres (PENDING) → Redis → Celery worker → Postgres (PROCESSED) → browser
```

Alongside it, introduce a migration tool as the single owner of the Postgres
schema in every environment.

The message feature is **deliberately throwaway**. It exists to exercise the
wiring and will be removed once real remittance flows land. The migration setup
is permanent.

## Scope

In scope:

- A `/integration-test` route on the frontend: one text input, a Send button, a
  List button.
- `POST /integration-messages` and `GET /integration-messages` on the API.
- A Celery task that transitions a message to `PROCESSED`.
- Migrations wired into local Docker Compose and the deploy pipeline.
- CORS on the API (previously absent; the feature cannot work in a browser
  without it).
- Test schema creation (previously broken; see "Schema ownership").

Out of scope: authentication on these endpoints, XRPL, any remittance domain
logic, pagination beyond a simple `limit`.

## Migration tool: Alembic, not Flyway

This was first designed around Flyway and changed during implementation.
SQLAlchemy has a companion migration tool, Alembic, whose `--autogenerate`
diffs the ORM metadata against a live database and writes the migration.

The deciding factor: with Flyway, the hand-written SQL and the
`IntegrationMessage` ORM model must be kept in step by hand — a standing drift
risk. Alembic makes the ORM the source of truth and derives the migration from
it, and `alembic check` turns "have these drifted?" into a command.

Secondary gains: no JVM or Docker image in CI, no second database URL in JDBC
format, migrations run from the existing API image, and `downgrade()` comes for
free.

Flyway remains the better choice when the ORM is *not* the source of truth —
for example if a non-Python service later owns tables. That is not the case
here.

Trade-off accepted: autogenerate is a strong first draft, not gospel. It is
reliable for tables, columns, indexes and foreign keys, and unreliable for
CHECK constraint changes on existing tables, server-default changes, some type
alterations, and anything needing a data backfill. Every generated file is
reviewed before commit.

## Migrations

### Layout

```
api/
  alembic.ini
  alembic/
    README.md          the standard, and how to add one
    env.py             URL + metadata from the app, not duplicated here
    script.py.mako     lint-clean template
    versions/
      V20260819_0040__create_integration_messages.py
```

Migrations live under `api/` because Alembic imports the application's models
and config. This also means the existing `api/**` path filter in
`deploy.yml` already covers them — no workflow trigger changes needed.

### Naming standard

```
V<UTC yyyyMMdd_HHmm>__<snake_case_summary>.py
```

Set automatically by `file_template` in `alembic.ini` with `timezone = UTC`, so
it is never typed by hand. Timestamps rather than sequential numbers: with `qa`
and `main` as branch-per-environment, two branches adding a migration on the
same day would otherwise collide.

The filename is for humans; Alembic's real ordering is the
`revision`/`down_revision` chain inside each file.

### Configuration

`alembic.ini` deliberately leaves `sqlalchemy.url` unset. `env.py` reads it from
`remitx_api.config.Config.DATABASE_URL` — the same root `.env` the API and
worker use — so there is one source of truth. `-x url=...` overrides it for
one-off targets.

### Execution

**Local** — a one-shot `migrate` service in `docker-compose.dev.yml`, built from
the API image, running `alembic upgrade head` once Postgres is healthy. The
`api` and `worker` services declare
`depends_on: migrate (service_completed_successfully)`, so neither can boot
against an unmigrated database.

**Cloud** — a `migrate` job in `deploy.yml`, `needs: [changes, ci, terraform]`
and gated on `push`, running `alembic upgrade head` against Neon using the
per-environment `MIGRATIONS_DATABASE_URL` secret. `deploy-api` and
`deploy-worker` gain `needs: migrate`, so a failed migration blocks the rollout
rather than leaving a running app on a schema it does not match.

### Lint interaction

The pre-commit hook runs `ruff check --fix` on every staged `api/**.py` *before*
`ruff format`. Autogenerated `op.*` calls run past 88 columns, and `E501` is not
auto-fixable, so every new migration would have blocked its own commit. Fixed
two ways: `script.py.mako` was rewritten to produce lint-clean imports, and
`alembic/versions/*.py` carries an `E501` per-file-ignore. `alembic` was added
to the CI ruff invocation so the directory is still checked.

## Schema

`integration_messages`:

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID` | primary key, generated by the API |
| `body` | `TEXT NOT NULL` | `CHECK (length(body) BETWEEN 1 AND 280)` |
| `status` | `TEXT NOT NULL` | `CHECK (status IN ('PENDING','PROCESSED'))` |
| `created_at` | `TIMESTAMPTZ NOT NULL` | |
| `processed_at` | `TIMESTAMPTZ NULL` | set by the worker |

Index on `created_at`. A single-column index serves `ORDER BY created_at DESC`
via a backward scan, so no descending index is needed.

`created_at` is set in Python rather than by a server default: SQLite's
`CURRENT_TIMESTAMP` has only second precision, too coarse to order the rapid
inserts in the ordering test.

The ORM model uses `sa.Uuid` and `DateTime(timezone=True)` so it also works on
SQLite under test.

## Schema ownership

`create_all()` was gated on `DEBUG`, which was wrong in two ways once a
migration tool exists:

1. Locally it would race Alembic and create tables Alembic did not author.
2. `TestConfig.DEBUG = False`, so **the test database had no tables at all** —
   latent while nothing touched the DB, fatal the moment anything did.

The gate is now an explicit flag: `Config.CREATE_ALL = False` (Alembic owns
Postgres), `TestConfig.CREATE_ALL = True` (tests own their throwaway SQLite).

`Database.init` also needed `StaticPool` and `check_same_thread=False` for
`sqlite:///:memory:`; without it each connection opens a *separate* empty
in-memory database, so tables created during setup are invisible to the next
caller. Extracted as `build_engine`, which the worker reuses.

## API

Layered per the existing convention — ORM → repository → controller → thin
route.

```
remitx_api/models/orm/integration_message.py
remitx_api/models/schemas/integration_message.py
remitx_api/repositories/integration_message_repository.py
remitx_api/controllers/integration_message_controller.py
remitx_api/services/queue_service.py
remitx_api/routes/integration_messages.py
```

### `POST /integration-messages`

Request `{"body": "..."}`. Pydantic strips surrounding whitespace and enforces
1–280 characters; violations return `422`.

The controller inserts the row as `PENDING`, **commits**, and only then
enqueues. The ordering is load-bearing: enqueueing inside the transaction races
the worker against a row it cannot yet read.

Responds `202 Accepted` with the full record.

### `GET /integration-messages?limit=50`

Newest first. `limit` is validated to 1–200 at the route.

### Enqueue, and the import cycle it caused

`queue_service` owns **its own** Celery producer rather than importing the
worker's app, and addresses the task by name:

```python
producer.send_task("remitx_worker.tasks.process_integration_message", ...)
```

The first implementation imported `remitx_worker.celery_app` from the API. That
deadlocked the worker at boot, and the reason is worth recording:
`remitx_api/__init__.py` eagerly imports `create_app`, so importing *any*
`remitx_api` submodule drags in the whole route tree. The worker imports
`remitx_api.config` → package init → app → routes → controller →
`queue_service` → back into the half-initialised `remitx_worker.celery_app`.

Giving the API its own producer makes the dependency one-directional
(`remitx_worker` → `remitx_api`, never back) and matches how the two actually
relate: the API needs a task name and a queue, never the task body. The queue
name lives on `Config.CELERY_QUEUE` so neither package imports the other to
learn it.

This is a latent trap for any future API→worker import. The underlying cause is
the eager import in `remitx_api/__init__.py`; worth revisiting separately.

### CORS

`CORSMiddleware`, origins from a comma-separated `CORS_ORIGINS` (default
`http://localhost:5173`). The API had none, so a browser could not call it
cross-origin at all.

## Worker

`remitx_worker/db.py` owns its engine and session factory, injectable for tests.
It cannot reuse `remitx_api.extensions.db`: that is a single request-scoped
session installed by HTTP middleware, invalid under Celery's prefork model.

`process_integration_message(message_id)` performs a conditional update:

```sql
UPDATE integration_messages
   SET status = 'PROCESSED', processed_at = now()
 WHERE id = :id AND status = 'PENDING'
```

`rowcount == 0` means already processed or unknown: log and return `"skipped"`
rather than raising.

That `AND status = 'PENDING'` is the duplicate-message protection. `acks_late`
is set, so redelivery is expected rather than exceptional, and the brief grades
duplicate protection explicitly.

## Frontend

`@tanstack/react-query` added, `QueryClientProvider` in `root.tsx`.

```
app/lib/api.ts                    typed fetch over VITE_API_URL, flattens FastAPI errors
app/lib/query-client.ts
app/routes/integration-test.tsx   registered in app/routes.ts
```

shadcn `input`, `table`, `alert` added; Button, Card, Badge already existed.

Auto-refresh is derived from the data rather than driven by a timer:

```ts
refetchInterval: (query) =>
  query.state.data?.some((m) => m.status === "PENDING") ? 1000 : false
```

It polls exactly while work is in flight and stops on its own — no cleanup, no
arbitrary timeout.

Client validation mirrors the server (trim, 1–280) with a live counter and a
disabled submit while invalid.

## Testing

**API** (`tests/test_integration_messages.py`) — `enqueue_integration_message`
monkeypatched, since CI has no Redis: validation rejections (empty,
whitespace-only, 281 chars), acceptance at exactly 280, `202` shape, enqueue
called once with the new id, newest-first ordering, `limit` honoured, empty
list, out-of-range limits rejected.

**Worker** (`tests/test_integration_message_task.py`) — session factory pointed
at a scratch SQLite file, task function called directly: PENDING becomes
PROCESSED; a second run returns `"skipped"` and leaves `processed_at`
unchanged; an unknown id is skipped rather than raising.

## Verification performed

Beyond the unit suite, the running stack was exercised directly:

- Compose ordering: postgres healthy → `migrate` ran → exited 0 → api and
  worker started.
- `alembic upgrade head` against real Postgres, then `alembic check` reporting
  "No new upgrade operations detected" — no ORM drift. `\d` confirmed both CHECK
  constraints and the index exist.
- `POST` → `202` PENDING with whitespace stripped; worker processed it ~400 ms
  later; `GET` showed PROCESSED with `processed_at`.
- Validation over HTTP: 422 for blank and 281 chars, 202 at 280, 422 for
  `limit=0`.
- CORS preflight from `http://localhost:5173` returning the expected
  `access-control-allow-origin`.
- **Duplicate protection against real Redis**: the same message id enqueued
  three more times; all three logged "already processed", `processed_at`
  unchanged.
- Browser: typed a message, sent it, table appeared newest-first. With the
  worker stopped, the row showed PENDING with an em-dash; restarting the worker
  flipped it to PROCESSED with no interaction, confirming the poll both runs and
  stops.

## Code review outcomes

Three reviewers covered the backend, the migration/CI surface, and the
frontend. Four issues were serious enough to change the design; all were
reproduced before being fixed.

**The shared session lost concurrent writes (backend, critical).** The
module-level `db` object held one session in a single attribute. FastAPI runs
sync routes in an anyio worker thread and serves requests concurrently, so one
request closed the session another was still writing through. Measured against
real Postgres: 24 concurrent POSTs produced 6 successes, 18 500s, and 15 rows.
Latent before this branch only because nothing wrote to the database. Fixed by
backing the session with a `ContextVar`; the same probe now returns 24/24 with
24 rows, and `tests/test_concurrent_requests.py` locks it in — verified to fail
against the pre-fix code.

**The deploy pipeline would have been a silent green no-op (infra, critical).**
GitHub applies an implicit `success()` to any job `if` without a status-check
function, and a *skipped* dependency fails it exactly as a failed one does. Any
push not touching `infra/**` would skip `terraform`, then skip `migrate` and
every deploy job, and still report the run green. All five previously
successful runs had `terraform` actually execute, so the path had never been
exercised. Every dependent job now leads with `!cancelled()`, which also means
the CI gate had to become explicit.

**CORS was never configured in Terraform (infra, critical).** `CORS_ORIGINS`
appeared nowhere in `infra/`, so the deployed API would fall back to its
`http://localhost:5173` default and reject every call from `qa.remitx.tech`.
Now derived in both environments from `swa_custom_domain` plus the SWA default
hostname.

**The poll never terminated when the worker was down (frontend, important).**
`refetchInterval` only checked for a `PENDING` row, so a stopped worker or a
dead API meant polling at 1 Hz forever — precisely the situations this page
exists to diagnose. Now bails out on query error and after a 60s ceiling, and
says so in the UI.

Also fixed: the worker raised instead of skipping on a malformed id; timestamps
serialized naive on SQLite and aware on Postgres, so the API contract differed
between tests and production; nothing verified that the producer's task name
matched the worker's registered task; CI never applied the migration at all
(now runs `alembic upgrade head` and `alembic check` against a Postgres
service); `env.py` would silently migrate a local SQLite file when
`DATABASE_URL` was unset; and the README's autogenerate recipe told you to diff
against an empty database, which emits `create_table` for every table.

## Accepted trade-offs

- Tests run on SQLite, so they validate application logic but not the migration
  itself. The migration is exercised by the Compose `migrate` service and the
  deploy job. Moving tests onto a Postgres service container is the upgrade path
  if PG/SQLite divergence bites.
- If the enqueue call fails after the commit, the row is stranded in `PENDING`.
  The correct fix is a transactional outbox; disproportionate for a feature
  scheduled for deletion.
- Adding a frontend dependency requires `npm install` inside the running
  frontend container, because `frontend_node_modules` is a named volume that
  shadows the host install. Pre-existing, not introduced here.

## Removal

When this feature is deleted, run `alembic revision -m "drop integration
messages"` after removing the model. The creating migration carries a header
comment saying so.
