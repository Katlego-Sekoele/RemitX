<h1 align="center">RemitX</h1>

<p align="center">
  A prototype cross-border FX remittance platform: senders in South Africa pay
  in rand, and settlement runs on the XRP Ledger <strong>Testnet</strong>.
</p>

---

RemitX is the class project for UCT's **ECO5040W: Financial Software
Engineering**. A sender deposits ZAR, gets a quote, and sends money to a
beneficiary. RemitX settles each transfer by burning a stablecoin on the XRPL
Testnet, then pays the beneficiary out in their own currency.

> [!IMPORTANT]
> This is an academic prototype. It uses the **XRPL Testnet only**, and no real
> customer funds, real remittances or production blockchain credentials are
> involved. Settlement uses `uctusd`, a lecturer-approved test token that
> stands in for RLUSD because the Testnet RLUSD faucet is rate-limited.

The full brief is in [docs/project-brief.md](docs/project-brief.md).

## How it works

1. **Sign up and verify.** A user signs up with Clerk, then completes a mock
   KYC application. The API validates identity documents by their leading
   bytes and stores them in private object storage. Compliance staff approve
   or reject each application in the admin portal. Only approved users can
   send.
2. **Deposit ZAR (simulated cash-in).** Every user gets their own payment
   reference, such as `sipho1-zar`. A treasury operator reconciles a bank
   statement against those references, which credits the sender's ZAR
   balance.
3. **Quote.** The sender picks a beneficiary and an amount. The quote freezes
   the exchange rate, fixed and percentage fees, FX margin, token amount,
   cash-out fee and estimated payout for 15 minutes. It is checked against
   the sender's daily and monthly limits.
4. **Confirm.** Confirming the quote writes every ledger leg of the transfer as
   `pending` in one commit. It then puts a settlement message on a Redis
   queue.
5. **Settle.** A Celery worker claims the transfer, burns the `uctusd` on the
   XRPL Testnet, and stores the transaction hash. It then confirms every leg
   together, or fails them all together. Guarded status transitions mean a
   redelivered message never settles a transfer twice.
6. **Pay out and withdraw.** The beneficiary sees the payout in their own
   currency account. Either user can withdraw a fiat balance to a bank
   account, less a cash-out fee.

The double-entry ledger, the seven legs of a remittance, fees, precision and
open questions are all written up in
[Transaction_Flow_Context.md](Transaction_Flow_Context.md). The KYC risk scoring
is in [docs/kyc-risk-rules.md](docs/kyc-risk-rules.md).

## Stack

| Layer | Technology |
|---|---|
| API | Python 3.11, FastAPI, SQLAlchemy, Alembic |
| Settlement worker | Celery with a Redis broker, `xrpl-py` |
| Frontend | React Router v7 (SPA), Tailwind v4, shadcn/ui, Aceternity UI |
| API client | Generated by Hey API from [frontend/openapi.json](frontend/openapi.json) |
| Auth | Clerk |
| Database | Postgres (Neon in the cloud, Docker locally). SQLite for unit tests |
| KYC documents | S3-compatible object storage (Neon Object Storage in the cloud, MinIO locally) |
| Hosting | Render (API and worker web services, static frontend, Key Value), provisioned with Terraform |

## Getting started

### Prerequisites

- Docker with Docker Compose
- Python 3.11 and Node 22, if you run the apps outside Docker
- A Clerk **development** application
- An [exchangerate-api.com](https://www.exchangerate-api.com) API key

### 1. Configure

A single root `.env` configures the API, the frontend and both compose files.

```bash
cp .env.example .env
```

At a minimum, fill in `CLERK_SECRET_KEY`, `VITE_CLERK_PUBLISHABLE_KEY` and
`EXCHANGE_RATE_API_KEY`. `.env.example` documents every other setting.

### 2. Create the platform wallet (optional)

You need this before transfers can settle on-chain. The script creates and
funds a Testnet account, opens its `uctusd` trust line, and writes the
encrypted seed and encryption key into `.env`:

```bash
pip install -r platform_wallet/scripts/requirements.txt
python platform_wallet/scripts/create_xprl_platform_wallet.py
```

Back up `XRPL_ENCRYPTION_KEY` somewhere other than the database. If you lose
it, the stored seed can't be recovered.

### 3. Run the stack

```bash
make up    # or: docker compose -f docker-compose.dev.yml up --build
```

This starts Postgres, Redis, MinIO, the API, the worker and the frontend. A
one-shot `migrate` service applies the Alembic migrations first.

| Service | URL |
|---|---|
| Frontend | http://localhost:5173 |
| API | http://localhost:4200 |
| API docs (Swagger UI) | http://localhost:4200/docs |
| MinIO console | http://localhost:9001 |

Stop it with `make down`.

To get from an empty database to a first deposit, see
[§9 of the transaction model](Transaction_Flow_Context.md#9-seeding-a-fresh-local-database).
The [QA seeder](tools/seeder/README.md) can also populate a local database with
realistic users, KYC applications and transfers.

### Running the apps without Docker

```bash
make api-install        # api/.venv with dev tools
make api-migrate        # alembic upgrade head against DATABASE_URL
make api-dev            # http://localhost:4200

make frontend-install
make frontend-dev       # http://localhost:5173
```

Run `make` to list every shortcut.

## Development

### Tests and checks

```bash
make api-test           # pytest (in-memory SQLite)
make api-lint           # ruff check --fix + ruff format
make frontend-lint      # typecheck + prettier --check
make frontend-test      # vitest
make seeder-test        # needs SEEDER_TEST_DATABASE_URL
```

The Postgres-only tests, such as the row-lock tests, run when
`TEST_DATABASE_URL` is set:

```bash
cd api && TEST_DATABASE_URL=postgresql+psycopg2://USER:PASSWORD@localhost:5432/postgres pytest -m postgres
```

### Git hooks

```bash
make hooks
```

The pre-commit hooks:

- regenerate `frontend/openapi.json` when the API changes
- run gitleaks, with custom rules for XRPL seeds and database URLs
- block any `.env` file from being committed
- run ruff, pytest, prettier and the frontend typecheck

### Changing the API

The OpenAPI spec is the frontend's contract. After you change a route, run
`make openapi` to regenerate `frontend/openapi.json`. The frontend client is
regenerated from it on `npm run dev`, `build` and `typecheck`. A test fails if
the committed spec is stale.

[CLAUDE.md](CLAUDE.md) covers the API's layering (routes → controllers →
repositories → ORM), migration rules and frontend UI conventions in detail.

### Load testing

```bash
make loadtest
```

This builds a throwaway stack, seeds it, runs Locust and writes a report to
`tools/loadtest/results/`. It never calls Clerk, the rate API or the XRPL. See
[tools/loadtest/README.md](tools/loadtest/README.md).

## Deployment

| Branch | Environment |
|---|---|
| `main` | QA |
| `stable` | Production ([remitx.tech](https://remitx.tech)) |

Feature branches target `main`. A release is a PR from `main` into `stable`.
GitHub Actions runs CI on every PR. On a push to `main` or `stable`, it applies
Terraform, runs the migrations and deploys to Render. See
[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md) and [infra/README.md](infra/README.md).

## Security

- XRPL seeds are encrypted at rest with a key held outside the database. They
  are never returned by the API, logged or committed.
- KYC documents live in a private bucket, never in Postgres. The API reads
  them through signed URLs that expire in minutes, and writes every read to
  the audit log.
- Staff access is role-based. Role changes and views of unmasked KYC details
  are written to the audit log too.
